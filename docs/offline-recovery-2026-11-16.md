# Offline recovery

Ordinary connected-account edits now use a typed, serializable outbox rather than closures held only in memory. `offline-journal.ts` atomically writes the local business view and ordered commands into one versioned record per authenticated user. Native storage uses the app's existing SQLite localStorage adapter; web uses browser localStorage. No auth tokens or payment links are added to this record.

On restart, sign-in selects only that user's cached business view. Pending commands replay before the server refresh; a failed refresh keeps the cached view and shows the save error. A stale startup read cannot overwrite pending local edits. Replay stops at a failed prerequisite and retries on foreground, every 30 seconds while work waits, or through `retryOffline`. Switching accounts prevents old completions from updating the new view and preserves the old account's outbox for its next sign-in.

Commands capture immutable arguments at save time. Customer, job, time, note, work-item, invoice, change-order, receipt, receipt-item and receipt-assignment creation reuse their client IDs with insert-on-conflict-ignore; an acknowledgement lost after one receipt stage can safely retry the remaining stages. Ordered replay ensures later edits do not overtake that receipt. Invoice/estimate mutable updates remain protected by server document locks.

`localSave` and `pendingSaves` separate “saved on this phone / waiting” from “confirmed by the account.” A storage error is reported as `failed`, keeps unrecorded commands in memory for retry, and blocks issuance. It must not be presented as a durable save; keep the app open until retry succeeds. Device/browser storage deletion, OS eviction, and clearing application data can still remove offline work. This cache is local app data, not a backup.

Final cash collection requires a connection and server acknowledgement. It is never stored in the ordinary outbox, so a changed balance, payment reservation, or permission error cannot permanently block unrelated edits. `markPaid(invoiceId, confirmedCents?)` returns `Promise<void>`: success means the server confirmed final cash collection (or the invoice was already confirmed paid); failure rejects without showing it paid. An optional confirmed amount lets the confirmation sheet reject a balance changed since it was shown. The server locks and derives the remaining balance, rejects stale amounts and in-flight online collections, and treats an already-paid invoice as a no-op. Deposits/partial collection use their separate request-ID API.

If initial local storage access fails, subsequent edits remain in an explicitly failed, in-memory buffer while KILN stays open. Retry opens only that authenticated account's journal, recovers its older pending commands, and atomically appends buffered commands with the CURRENT edited view; it does not restore a stale cached view over new edits. No success is shown until local storage works, and server confirmation still waits for replay. Closing the app before a failed local save is rescued can lose the memory-only work.

Sending/signing remain online, server-confirmed operations. The durable outbox drains before issuance. Native photo files retain their existing separate retry queue; web photos waiting in a tab are still not a durable image-file queue. Voice text can be saved as an ordinary note; recordings are not retained.

Tests in `offline-journal.test.ts` cover offline restart, dependency failure/retry, immutable arguments, switching accounts during a request, lost acknowledgements with the same operation ID, appending during replay, storage-full failures, and wrong-owner/corrupt records. `save-queue.test.ts` continues to cover document barriers. These unit tests do not establish actual device power-loss behavior, local-storage encryption, or deployed backend migration status.
